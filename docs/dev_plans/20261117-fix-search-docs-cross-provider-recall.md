# `search_docs` misses cross-provider additions (speaker diarization, 1.16): document the limitation

## Status

Decision (grilled 2026-11-18, after `/review-plan` round 4; rounds 5-8 reviewed the limitation plan): **document the limitation and add one advisory paragraph to the MCP server instructions; no retrieval, ranking or ingest code change.** On 2026-11-19, after the Phase 0 measurements, the user chose to fold the caller-facing hint into this branch (it was a Follow-up); round 11 of `/review-plan` reviewed that paragraph. Branch `fix/search-docs-cross-provider-recall`. Split out of #166 (closed). On 2026-11-19 the user chose not to file a new GitHub issue: the PR description carries the Phase 0 results and the two Follow-up items. Lifecycle state lives below the review marker (the Progress checklist, which also records the Phase 0 HEAD, Phase 0 main, index refresh time and framework version) and in this plan's row of `docs/dev_plans/README.md`, so recording progress never edits the reviewed contract.

Earlier revisions planned a ranking fix (a per-page cap, cross-encoder windows, table splitting). Round 4 measured that none of them can deliver a defensible Goal; "What we know" records why, and "Follow-up" keeps the findings worth their own plans.

## Goal

Record, against the live index, which calls return the STT providers' diarization settings, and publish that in the PR description, a `docs/smoke-test.md` item (numbered in Phase 1: the next free number, 61 while main ends at 60) and one paragraph in the MCP server instructions. The audience is maintainers, issue reporters and MCP agents. The paragraph (Phase 1 step 2) tells an agent that a settings query shared by several providers can return only some providers' Settings chunks while `low_confidence` is `false`, that `limit=20` returns more of them, and that `get_doc` on the exact `.md` path is the route for one provider. It promises no full coverage, and it must fit a character budget because one client shows only the first 4096 characters of the instructions ("What we know"). It is advisory prose: it changes no ranking, a caller at a small `limit` still gets the same hits, the CLI's stderr hint (gated on `low_confidence` or empty results) does not change, and whether an agent acts on the paragraph is not measured. The measurements use the working-tree CLI, which shares the MCP handlers; the MCP client runs the installed tool, so the PR description records the CLI's package version beside the result, and that the retrieval and index code is unchanged since that release tag (the version string alone does not show it).

Scope: the twelve STT pages listed in "What we know", each with a settings table row naming `speaker_format` or `diarize` and each returned by `limit=20`. Thirteen pages meet the table-row criterion; Hakim is the thirteenth and `limit=20` does not return it, so the scope is the list, not the criterion. The token match is a proxy for "diarization settings": a page that names the setting differently is not covered (the review named Oruk and Gnani; not measured here). Known misses: Hakim (`stt/hakim.md`, a `diarize` row only, outside the top 50; not measured further), and two other misses from #166, `TranscriptionFrame.speaker` (`frames/data-frames.md`) and the RTVI `speaker` field (`standards/rtvi-standard.md`). `limit=20` returns neither of those two (first hit at rank 33 and 23 at `limit=50`; Phase 0 step 5(b) re-takes both); the exact `.md` path via `get_doc` returns each page. The workarounds, for the index measured (framework 1.16.0, refreshed 2026-11-18):

1. `search_docs("speaker diarization speaker_format", limit=20)` returns a *qualifying hit* for each of the twelve pages. A qualifying hit is one whose chunk text (`get-doc --doc-id <hit doc_id>`) has a table row, a line that starts with `|`, naming `speaker_format` or `diarize`. The hit's `section` field is not the test: it can be null. The margin is thin (the last qualifying hit sits at rank 19 of 20), so this is an observation for this index, not a guarantee.
2. `get_doc(path="/api-reference/server/services/stt/<page>.md", section="Settings")` returns the page's *first* Settings section, which starts with `## Settings` and has a table row (a line starting with `|`) naming `speaker_format` or `diarize`. On a page with several Settings sections (one per service) it returns the first service's settings only; NVIDIA's second Settings section also has a `speaker_format` row, so workaround 2 does not reach it.

The server instructions (`src/pipecat_context_hub/server/main.py:129-133`) tell an agent to raise `limit` to 20 and try `get_doc` only on `low_confidence`, zero hits or a user complaint, so none fires for this query.
- **One client cuts the instructions at 4096 characters.** `_SERVER_INSTRUCTIONS` is 6,866 characters. The "Corpus hint" block spans offsets 2948-4026 (its last sentence, "do not file it yourself.", ends at 4024) and the "degraded hub" block starts at 4026. Inserting text before the Corpus hint pushes its trust warnings ("not vetted by the catalog", "reaches you unfiltered", "do not file it yourself") past the cut unless equal text is trimmed earlier.
- **Other settings queries and pages differ from diarization.** In review round 11, `search_docs("language setting speech-to-text", limit=20)` returned 9 of the 37 STT pages that have a `language` table row (reranker on; dated, not re-run here), and 10 of 44 STT pages have no `## Settings` heading, so `section="Settings"` returns the whole page there. Both facts are why the instructions paragraph promises no coverage.
- **A per-provider query is not a workaround.** `search_docs("<Provider> speech-to-text diarization", limit=5)` returns the provider's title, Overview or TTS-page chunks and never a Settings chunk (0 of 10 across ElevenLabs, AWS Transcribe, OpenAI, Deepgram and Soniox, both modes). The multi-concept form `search_docs("speaker diarization + speaker_format", limit=14)` returned ten hits and none qualifies (reranker on, review round 9; dated); it is not a workaround either.
- **`get_doc` needs the exact `.md` path, and a bad section fails silently.** `get_doc` on `stt/<page>` or the path without `.md` returns `Not Found` with exit 0; the same holds for `/guides/learn/transports` and `/guides/telephony/overview` (with or without `.md`), the examples shown in `AGENTS.md`, `docs/cli.md`, `docs/tools.md` and the tool descriptions. A section that matches nothing returns the whole page with no error (`services/retrieval/hybrid.py:429-432`), so the check that the section matched is that the content starts with `## Settings`. Only the first matching section is returned (`shared/markdown.py:91`). The response's `sections` list is deduplicated (`shared/markdown.py:124-140`) and always shows one "Settings", so the number of Settings sections is the count of `^## Settings` lines in the full page content (NVIDIA 3, Deepgram 4, ElevenLabs 2, OpenAI 2; Phase 0 step 4 re-takes them).
- **The CLI hides chunk text.** `search-docs` returns a 300-character snippet per hit (`services/retrieval/hybrid.py:345`), and the first `speaker_format` or `diarize` match sits at character 1864 or later of each Settings chunk (a dated note), so the snippet cannot show whether a chunk qualifies. `get-doc --doc-id` returns the chunk text (a Settings continuation chunk starts with `| Parameter`, not a heading).
- **Why no ranking change fixes it.** The Settings chunks are near-identical tables for different providers, and no query-independent signal prefers five of them over the other seven; scores run 2.2e-5 to 9.8e-5 with the reranker on. A per-page cap or reorder of the cross-encoder window (`top_n` = 20, `shared/config.py:207`) cannot change which 20 chunks return. Windowed cross-encoder scoring re-scores the same 20 candidates. Whether the 512-token ceiling (`services/onnx_backend.py:73`) cuts the diarization rows is not established (a guess; at least one chunk's rows start inside it), so the plan does not rely on it. A hypothesis, not measured: fixing table markup would lift all table chunks alike (see Follow-up).
- **Reranker default.** `RerankerConfig.enabled` defaults to `True` (`shared/config.py:181-182`); `serve` and the CLI run reranker-off when the config disables it, when the model is not cached (`shared/reranker.py:32`) or when it fails to load (`shared/reranker.py:58-82`). `status` reports `reranker_enabled` and `reranker_disabled_reason`. The `RerankerConfig` docstring ("Enable via ``PIPECAT_HUB_RERANKER_ENABLED=1`` ... Disabled by default.", `shared/config.py:177-178`) and the `AGENTS.md` Review Checklist entry "Confidence scores are optimistic on weak `search_examples` results" (2026-03-24, which says the cross-encoder is "disabled by default") are stale. `docs/configuration.md` and `docs/reranking.md` already say it is on.

### Follow-up (not in this plan)

Recorded in the PR description, not in a new issue (decided 2026-11-19).

- **Table-markup compaction at ingest**, for its own goal (embedding and cross-encoder quality on every table chunk in the corpus). What the reviews established: the separator row of a markdown table costs hundreds of embedding tokens (one WordPiece token per dash; a review measured 828 on AssemblyAI's chunk), so a table chunk's embedding can be mostly dashes. A fix needs a compaction step in `docs_crawler.py`; a skip marker bound to the content hash (store `<chunker_version>:<content_hash>` next to the raw `docs:content_hash`, drop both in `_distrust_skip_markers` and the write-ahead delete); `get_doc` handling if tables are split; and attention to the vector store's metadata allowlist (`services/index/vector.py:107-180` drops `title`, `section` and any new key).
- **`title` and `section` lost on vector-first hits.** The vector store drops both (`services/index/vector.py:107-180`), so a vector-first hit carries the page path as `title` and a null `section` (`hybrid.py:345`). This is caller-visible, independent of table compaction, and makes a hit harder to read and to attribute to a page; it needs its own plan.

### Out of scope

- Any change to ranking, the cross-encoder, `top_n`, ingest or chunking. A response-level hint (a field like `corpus_hint`) or a change to the CLI's stderr hint: either needs a trigger that detects cross-provider settings queries, which is not designed or measured.
- A counterpart to the instructions paragraph in the CLI's `search-docs --help` text: the paragraph reaches MCP agents only (accepted).
- A hub-side "capability matrix" built from release notes.
- Upstream docs changes (a prose section per provider); a possible outcome, not planned here.
